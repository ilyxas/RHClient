## 2. Архитектура клиента (кратко)

```
RHClient.xcodeproj
├─ RHClient/              приложение, SwiftUI, iOS 27, Swift 6 (strict concurrency)
│   ├─ App/               точка входа, таб-бар Home · Chat · Terminal · Log · Pages, Face ID-сессия
│   ├─ Features/          Pairing, Home, Chat, Terminal, Log, Pages, Settings, Approval
│   └─ UI/                единая библиотека компонентов (DESIGN.md): MetricCard, StatusRow,
│                         ActionTile, … — из неё собраны и Home, и страницы rh.page/1
├─ Packages/RHKit/        локальный Swift Package, без UI
│   ├─ RHCrypto           JCS (RFC 8785), KeyProvider, подпись запросов, проверка X-RH-Server-Sig
│   ├─ RHAPI              HTTP-клиент, challenge, ошибки → состояние соединения, WebSocket
│   ├─ RHPages            модели rh.page/1, строгий декодер, валидатор, выражения visibleWhen/enabledWhen
│   └─ RHModels           значения data_id (number/string/bool/status/rows/text), журнал, approvals
├─ RHClientTests/ + Packages/RHKit/Tests/   юнит-тесты, контрактные тест-векторы
├─ RHClientUITests/       XCUITest против rh-core dev-режим + rh-agent fake-режим
├─ contracts/             копия contracts/ из RHServer, зафиксированная на коммит (UPSTREAM)
├─ scripts/               sync-contracts.sh, test.sh, check-*.py (проверки без Xcode)
└─ docs/decisions/        закрытые [проверить] с источниками
```

Принципы:
- Сторонних зависимостей нет, пока Илья не утвердит библиотеки Markdown (этап 3) и SSH/терминала (этап 6). Всё остальное — системные фреймворки (CryptoKit, Security, LocalAuthentication, VisionKit, PhotosUI, URLSession).
- JCS пишу сам (в Swift нет стандартной реализации), проверяю векторами сервера.
- Тестовые швы только в Debug: `SoftwareKeyProvider`, pairing-строка из буфера обмена или аргумента запуска, `http://127.0.0.1` через `NSAllowsLocalNetworking`. В Release их нет; на этапе 7 это проверяет тест.
- Уровень ключа проверяет сервер (SPEC §4.1). Клиент выбирает ключ по `x-rh-key` операции из openapi и не пытается сам что-то «разрешать».

## 3. Стыки с RHServer

- `contracts/` живёт в корне RHServer, ведёт агент сервера, я ревьюю каждое изменение. В RHClient — копия `contracts/` и файл `contracts/UPSTREAM` с sha коммита RHServer; обновление — `scripts/sync-contracts.sh <sha>`, отдельным коммитом «sync contracts @sha». Сабмодуль не беру: Илье и Xcode проще без `--recursive`.
- Форматы, которые фиксируем в `contracts/` до этапа 1 (предложено серверу, ждёт согласования): формат `ts`/`exp`; base64 по RFC 4648 §4; `body` = sha256 сырых байт, hex; подписываются UTF-8 байты канонического JSON; публичные ключи — X9.63 uncompressed в base64; формат `X-RH-Server-Sig`; `x-rh-op` и `x-rh-key` у каждой операции; машиночитаемые коды отказа; формат pairing-строки (QR); отпечаток устройства.
- Тест-векторы, которые проходит клиент: канонический JSON; проверка подписи; сборка `X-RH-Auth` из фиксированного тестового ключа; проверка подписи ответа ядра; страницы valid/invalid с ожидаемым текстом ошибки (этап 5).
- Мок-сервер (PROCESS, «Цикл этапа» п.2): юнит-тесты клиента идут на заглушке `URLProtocol` с фикстурами из примеров `openapi.yaml`, подписанными тестовым ключом ядра из векторов. Интеграция — настоящий rh-core в dev-режиме и rh-agent в fake-режиме. Отдельный мок без подписей не делаю: клиент обязан отвергать неподписанные ответы.

### Этап 1. Доверие

**Задачи**
- `KeyProvider`: `SecureEnclaveKeyProvider` (ключи `normal`, `critical`, `ssh`; `.privateKeyUsage` + `.biometryCurrentSet`, без fallback на код) и `SoftwareKeyProvider` (только Debug, для симулятора).
- Face ID-сессия: один `LAContext` для `normal`, пока приложение активно; сброс после N минут в фоне (по умолчанию 5, настройка в Settings); для `critical` — свежий контекст на каждую подпись.
- Подпись запроса: `POST /v1/challenge` → канонический объект → `X-RH-Auth`, `X-RH-Sig`. Проверка `X-RH-Server-Sig` ключом ядра из pairing; ответ без валидной подписи — ошибка.
- Состояние соединения: `Connected · Secure session` / `Unreachable` / `Auth error` / **Pairing lost**. Pairing lost — при недоступных ключах (смена биометрии, переустановка), несовпадении ключа ядра, отказе `revoked`/`unknown_device`. Без падений и «тихих» ошибок сети.
- Pairing: сканер QR (VisionKit), разбор pairing-строки, создание ключей, запрос с подписями `normal` и `critical`, показ отпечатка устройства (тот же, что в терминале), сохранение ключа ядра и device_id в Keychain. В симуляторе — строка из буфера обмена или аргумента запуска.
- Экран Pairing lost с кнопкой **Re-pair**; Re-pair в Settings.
- Подписанный `ping` и экран статуса.
- Settings → Devices: список и **Revoke** (ключ `critical`).
- Публичный ключ `ssh` уходит в pairing-запросе сразу (если сервер примет поле), чтобы этап 6 не требовал повторного pairing.

**Тесты**
- Юнит: векторы подписи и проверки; сборка `X-RH-Auth` байт-в-байт; проверка подписи ответа (валидная, чужой ключ, изменённое тело, изменённый статус); отображение каждого кода отказа в состояние; Pairing lost при недоступном ключе (заглушка KeyProvider); разбор pairing-строки (валидные и битые).
- UI (симулятор, dev rh-core): pairing из аргумента запуска → ping → экран статуса; revoke → Pairing lost → Re-pair.
- Отказы со стороны ядра (повтор nonce, просрочка, чужой ключ, отозванное устройство, неверный уровень, часы, тело) тестирует сервер; клиент проверяет, что каждый из них показан правильно.

**От сервера** — `challenge`, `pair`, `ping`, `devices` в openapi; все векторы подписи; формат pairing-строки и отпечатка; коды отказа; dev-режим ядра на `127.0.0.1` с приёмом программных ключей.

**[проверить]** (записи в `docs/decisions/`)
- переиспользование `LAContext` для подписи ключом Secure Enclave (`kSecUseAuthenticationContext`), поведение `.biometryCurrentSet` при смене биометрии и как это распознать;
- сертификат `tailscale cert` проходит ATS без исключений (совместно с сервером, §3.3);
- заголовки на upgrade-запросе `URLSessionWebSocketTask` (нужно для `ws.open` на этапе 3, но проверяю сейчас вместе с подписью).

**Илья** — установка сборки на iPhone (подпись в Xcode, пошаговая инструкция от меня); реальный pairing по QR; проверка Face ID на устройстве (обязательная физическая приёмка, SPEC §9.1).

### Этап 4. Approvals

**Задачи**
- Needs Attention → экран approval: полный текст операции, объяснение агента, ожидаемые последствия; **Allow once** (`critical`, свежий Face ID) и **Deny** (`normal`).
- Подпись привязана к `approval_id` и sha256 текста операции; хеш клиент считает сам по тем байтам, которые показывает.
- Карточки approvals в ленте чата рядом с сообщением агента.
- Stop / Reset снимают ожидание (равносильно Deny).
- Тексты UI не утверждают, что approval гарантирован для всех операций (SPEC §2).

**Тесты** — хеш операции по фиксированным векторам; выбор ключа по операции; UI на сценариях fake rh-agent: Allow, Deny, отмена через Stop и Reset, ожидание без таймаута.

**От сервера** — API очереди approvals, формат операции и правило хеширования, события сокета о новых approvals и их снятии.

**[проверить]** — нет своих; серверный callback SDK закрывает сервер.

**Илья** — физическая проверка Allow / Deny с Face ID на iPhone (обязательна по SPEC §9.1); утверждение начального списка критических операций — у сервера.

### Этап 5. Pages

**Задачи**
- `RHPages`: модели `rh.page/1`, строгий декодер (неизвестный ключ — ошибка с понятным текстом, тем же, что у `rhpage validate`), лимиты 12 секций / 60 компонентов, выражения `bind`/`eq`/`neq`/`gt`/`lt`/`and`/`or`/`not`.
- Рендер пяти layout и девяти компонентов из той же библиотеки, что Home. Состояния элемента: unbound, pending, active, running, error. Ссылка на незарегистрированный action/data — pending, не ошибка. Невалидная страница — состояние **Invalid** с текстом, не падение.
- Опрос data_id по их интервалам, пока страница открыта.
- Вызов action: ключ по `risk` (`critical` — свежий Face ID), `confirm: true` — локальный диалог, параметры из полей ввода, показ `message` и обновление связанных данных.
- Pages: список с бейджами Draft / Invalid / Pending; Draft → **Accept** (`normal`); «Ожидают регистрации» с **Register** (`critical`).
- Правка на телефоне: переименовать, переставить секции и компоненты, удалить компонент, закрепить в Quick Access; **+ Page** → Chat с подготовленным запросом.
- Quick Access на Home заполняется.

**Тесты** — все page-векторы valid/invalid с совпадением текста ошибки; таблица тестов выражений; каждый компонент и layout рендерится; UI: страница от fake rh-agent с кнопкой, toggle и списком.

**От сервера** — `contracts/pages/rh.page.v1.schema.json`, page-векторы, API страниц (список, версия, Accept, правки с телефона, Quick Access), реестры action/data, вызов action.

**[проверить]** — нет своих.

**Илья** — приёмка: агент по запросу в чате создаёт рабочую страницу с кнопкой, toggle и списком.
