│   ├─ RHAPI              HTTP-клиент, challenge, ошибки → состояние соединения, WebSocket
│   ├─ RHPages            модели rh.page/1, строгий декодер, валидатор, выражения visibleWhen/enabledWhen

├─ RHClientUITests/       XCUITest против rh-core dev-режим + rh-agent fake-режим
├─ contracts/             копия contracts/ из RHServer, зафиксированная на коммит (UPSTREAM)
├─ scripts/               sync-contracts.sh, test.sh, check-*.py (проверки без Xcode)
└─ docs/decisions/        закрытые [проверить] с источниками

Принципы:
- Сторонних зависимостей нет, пока владелец не утвердит библиотеки Markdown (этап 3) и SSH/терминала (этап 6). Всё остальное — системные фреймворки (CryptoKit, Security, LocalAuthentication, VisionKit, PhotosUI, URLSession).
- JCS пишу сам (в Swift нет стандартной реализации), проверяю векторами сервера.
- Тестовые швы только в Debug: `SoftwareKeyProvider`, pairing-строка из буфера обмена или аргумента запуска, `http://127.0.0.1` через `NSAllowsLocalNetworking`. В Release их нет; на этапе 7 это проверяет тест.
- Уровень ключа проверяет сервер (SPEC §4.1). Клиент выбирает ключ по `x-rh-key` операции из openapi и не пытается сам что-то «разрешать».

## 3. Стыки с RHServer

Протокол и формат векторов согласованы с агентом сервера; источник — раздел «Протокол: конкретизация SPEC §4» в `RHServer/PLAN.md`. Здесь — то, что касается клиента.

### `contracts/`: где живёт и как не разъезжается

- Оригинал — `contracts/` в корне RHServer. Ведёт агент сервера. Любое изменение — PR в RHServer, я ревьюер, мержит владелец.
- В RHClient — копия `contracts/`, плюс два файла:
  - `contracts/UPSTREAM` — sha коммита RHServer, с которого снята копия, и корневой хеш манифеста;
  - `contracts/MANIFEST.sha256` — sha256 каждого файла контракта в формате `sha256sum` (`<hex>  <путь относительно contracts/>`, сортировка по пути, сам манифест в список не входит). Корневой хеш в `UPSTREAM` = sha256 байт файла манифеста. Манифест генерирует и проверяет сервер у себя, в копию он попадает как есть.
- Копия не может молча разойтись с оригиналом, это проверяют два теста, оба красные при несовпадении:
  1. **Юнит-тест клиента** (`ContractsIntegrityTests`, гоняется с `xcodebuild test`): sha256 каждого файла в бандле совпадает с `MANIFEST.sha256`, корневой хеш совпадает с записанным в `UPSTREAM`; лишних и недостающих файлов нет. Ловит ручную правку копии.
  2. **`scripts/check-contracts.sh`** (Linux-джоба CI или вручную): берёт RHServer на коммите из `UPSTREAM` и сравнивает побайтно. Ловит подмену манифеста и неверный `UPSTREAM`. Если в `main` RHServer контракт уже новее, джоба об этом сообщает, но не падает: новую версию я подтягиваю осознанно.
- Обновление копии — только `scripts/sync-contracts.sh <sha>`, отдельным коммитом «sync contracts @<sha>» с указанием PR в RHServer, из которого пришли изменения. Руками копию не правлю.
- Почему не submodule: submodule подключает весь репозиторий RHServer, а не одну папку, и требует `--recursive` и доступа к RHServer при каждой сборке в Xcode. Если владелец предпочтёт submodule, переход простой: тесты читают те же пути.

### Форматы (кратко, полностью — в `contracts/`)

- Публичные ключи — X9.63 uncompressed, base64 RFC 4648 §4; `device_id` = первые 32 hex `sha256(normal_pub)`, считает клиент.
- `ts`/`exp` — `YYYY-MM-DDTHH:MM:SSZ`; `body` — sha256 сырых байт, hex; подписываются байты JCS-объекта; в подписываемых объектах только строки, целые, объекты и массивы, без дробных чисел.
- `op` и уровень ключа закреплены за операцией (`x-rh-op`, `x-rh-key` в openapi).
- `X-RH-Server-Sig` — ключом ядра над JCS `{v, nonce, status, body}`; подписаны и отказы. Клиент отвергает ответ без валидной подписи.
- Отказы — `{"error":{"code","message"}}`. Коды `unknown_device`, `revoked_device` и несовпадение ключа ядра → **Pairing lost**; остальные → **Auth error**; нет ответа → **Unreachable**.
- Pairing-строка `rhpair:` + base64url(JCS); отпечаток — 16 hex группами по 4, одинаковый в терминале и на телефоне.
- WebSocket: кадры с `seq` и подписью ядра; после переподключения состояние берётся через REST.

### Тест-векторы

Самая важная часть контракта: одни и те же файлы гоняют тесты обеих сторон, расхождение сериализации ловится в первый день, а не на pairing с iPhone. Клиент проходит: `jcs.json` (scope `protocol`, этап 0), `ecdsa.json`, `request_build.json`, `server_sig.json`, `pairing.json` (этап 1), `ws_frames.json` (этап 3), хеш операции approval (этап 4), `pages/valid|invalid` (этап 5), `ssh_pubkey.json` (этап 6). `signed_requests.json` гоняет сервер; клиент берёт из него коды отказов для текстов в UI.

### Мок-сервер

- Мок собирается из `openapi.yaml`: примеры ответов из спецификации, подписанные тестовым ключом ядра из векторов, отдаются заглушкой `URLProtocol` внутри тестов и Debug-сборки. Подпись нужна, потому что клиент обязан отвергать неподписанные ответы, поэтому готовый Prism-мок без подписей не подходит. Тест проверяет, что у каждой операции из openapi есть пример ответа: появилась операция — мок о ней знает.
- На моке я делаю UI этапа, не дожидаясь сервера. Интеграция — настоящий `rhcore dev up` (127.0.0.1:8787) и `rh-agent --fake <сценарий>`.

### Согласовано с сервером дополнительно (RHServer PR #1, коммит 67b0a8c)

- Подпись ответа: для challenge `nonce` = выданный nonce (для отказа `""`), для pair — код из QR; все случаи в `server_sig.json`.
- `POST /v1/pair` держит соединение до `y`/`n` в терминале (≤ 5 мин): 200 с device_id / 403 `pair_rejected` / 403 `bad_pair_code`.
- Поле `replaces` в pair: повторный pairing после смены биометрии отзывает старую запись, хотя device_id новый.
- Необязательное `ssh_host_keys` в подписанном ответе pair с этапа 1 (решение И4 за владельцем); ключ `ssh` в запросе pair обязателен.
- `rhcore ssh authorize <device>` на этапе 6, чтобы не делать re-pair.
- `op_sha256` = sha256 UTF-8 байт JCS-объекта операции; клиент показывает поля того же объекта; вектор `approval_hash.json`. Поэтому массивы входят в JCS scope `protocol`.
- `attach.upload` — сырое тело, `Content-Type` + `X-RH-Filename` (percent-encoded UTF-8), хеш считается потоково.
- `risk` каждого action_id в ответах реестра и страниц: клиент заранее знает, нужен ли Face ID.

### Этап 1. Доверие

**Задачи**
- `KeyProvider`: `SecureEnclaveKeyProvider` (ключи `normal`, `critical`, `ssh`; `.privateKeyUsage` + `.biometryCurrentSet`, без fallback на код) и `SoftwareKeyProvider` (только Debug, для симулятора).
- Face ID-сессия: один `LAContext` для `normal`, пока приложение активно; сброс после N минут в фоне (по умолчанию 5, настройка в Settings); для `critical` — свежий контекст на каждую подпись.
- Подпись запроса: `POST /v1/challenge` → канонический объект → `X-RH-Auth`, `X-RH-Sig`. Проверка `X-RH-Server-Sig` ключом ядра из pairing; ответ без валидной подписи — ошибка.
- Состояние соединения: `Connected · Secure session` / `Unreachable` / `Auth error` / **Pairing lost**. Pairing lost — при недоступных ключах (смена биометрии, переустановка), несовпадении ключа ядра, отказе `revoked_device`/`unknown_device`. Без падений и «тихих» ошибок сети.
- Pairing: сканер QR (VisionKit), разбор pairing-строки, создание ключей, запрос с подписями `normal` и `critical`, показ отпечатка устройства (тот же, что в терминале), сохранение ключа ядра и device_id в Keychain. В симуляторе — строка из буфера обмена или аргумента запуска.
- Экран Pairing lost с кнопкой **Re-pair**; Re-pair в Settings.
- Подписанный `ping` и экран статуса.
- Settings → Devices: список и **Revoke** (ключ `critical`).
- Публичный ключ `ssh` уходит в pairing-запросе сразу (согласовано), чтобы этап 6 не требовал повторного pairing. В тот же запрос — `replaces` с прошлым device_id из Keychain, если он есть.
- Debug-пункт Settings → «Export test signature»: публичный ключ, JCS-объект ping и DER-подпись настоящего Secure Enclave в буфер обмена. Сервер добавляет это вектором в `ecdsa.json`, и совместимость DER проверена на реальном железе.

**Тесты**
- Юнит: векторы подписи и проверки; сборка `X-RH-Auth` байт-в-байт; проверка подписи ответа (валидная, чужой ключ, изменённое тело, изменённый статус); отображение каждого кода отказа в состояние; Pairing lost при недоступном ключе (заглушка KeyProvider); разбор pairing-строки (валидные и битые).
- UI (симулятор, dev rh-core): pairing из аргумента запуска → ping → экран статуса; revoke → Pairing lost → Re-pair.
- Отказы со стороны ядра (повтор nonce, просрочка, чужой ключ, отозванное устройство, неверный уровень, часы, тело) тестирует сервер; клиент проверяет, что каждый из них показан правильно.

**От сервера** — `challenge`, `pair`, `ping`, `devices` в openapi; все векторы подписи; формат pairing-строки и отпечатка; коды отказа; dev-режим ядра на `127.0.0.1` с приёмом программных ключей.

**[проверить]** (записи в `docs/decisions/`)
- переиспользование `LAContext` для подписи ключом Secure Enclave (`kSecUseAuthenticationContext`), поведение `.biometryCurrentSet` при смене биометрии и как это распознать;
- сертификат `tailscale cert` проходит ATS без исключений (совместно с сервером, §3.3);
- заголовки на upgrade-запросе `URLSessionWebSocketTask` (нужно для `ws.open` на этапе 3, но проверяю сейчас вместе с подписью).

**Владелец** — установка сборки на iPhone (подпись в Xcode, пошаговая инструкция от меня); реальный pairing по QR, сверка отпечатка на телефоне и в терминале; проверка Face ID на устройстве (обязательная физическая приёмка, SPEC §9.1); «Export test signature» и прислать результат в тред.

**[проверить]** — актуальные API Liquid Glass в iOS 27 SDK. В конце этапа исследую библиотеки Markdown (§8.3), чтобы владелец утвердил выбор до этапа 3.

**Владелец** — посмотреть Home на iPhone с живыми данными (приёмка этапа); утвердить библиотеку Markdown **[утвердить]**: дам 2–3 варианта с плюсами и минусами.

### Этап 3. Chat

**Задачи**
- Лента чата; отправка — подписанный `chat.send`; стрим ответа по WebSocket (`ws.open`); индикатор «агент работает»; **Stop**.
- Markdown: заголовки, списки, код с подсветкой, таблицы, ссылки — утверждённой библиотекой.
- Вложения: фото, Files, камера; подписанная загрузка (лимит из настроек ядра, по умолчанию 25 МБ), хеш тела считается потоково.
- Индикатор контекста в процентах, по тапу — числа.
- **Reset session** с локальным подтверждением.
- Место для карточек approvals в ленте (сами карточки — этап 4).

**Тесты** — разбор событий WebSocket, склейка стрима, повторное подключение и дедупликация; подпись загрузки; UI на сценариях fake rh-agent (стрим, usage, Stop, Reset).

**От сервера** — `chat.send`, `ws.open`, схема событий сокета, загрузка вложений, usage и размер окна, имена сценариев fake-режима для UI-тестов.

**[проверить]** — выбранная библиотека Markdown на iOS 27 (рендер таблиц и кода, производительность при стриме).

**Владелец** — диалог с агентом с телефона; проверить, что сообщения есть в CGC (приёмка).

### Этап 4. Approvals

**Задачи**
- Needs Attention → экран approval: полный текст операции, объяснение агента, ожидаемые последствия; **Allow once** (`critical`, свежий Face ID) и **Deny** (`normal`).
- Подпись привязана к `approval_id` и sha256 текста операции; хеш клиент считает сам по тем байтам, которые показывает.
- Карточки approvals в ленте чата рядом с сообщением агента.
- Stop / Reset снимают ожидание (равносильно Deny).
- Тексты UI не утверждают, что approval гарантирован для всех операций (SPEC §2).

**Тесты** — хеш операции по фиксированным векторам; выбор ключа по операции; UI на сценариях fake rh-agent: Allow, Deny, отмена через Stop и Reset, ожидание без таймаута.

**От сервера** — API очереди approvals, формат операции и правило хеширования, события сокета о новых approvals и их снятии.

**[проверить]** — нет своих; серверный callback SDK закрывает сервер.

**Владелец** — физическая проверка Allow / Deny с Face ID на iPhone (обязательна по SPEC §9.1); утверждение начального списка критических операций — у сервера.

### Этап 5. Pages

**Задачи**
- `RHPages`: модели `rh.page/1`, строгий декодер (неизвестный ключ — ошибка с понятным текстом, тем же, что у `rhpage validate`), лимиты 12 секций / 60 компонентов, выражения `bind`/`eq`/`neq`/`gt`/`lt`/`and`/`or`/`not`.
- Рендер пяти layout и девяти компонентов из той же библиотеки, что Home. Состояния элемента: unbound, pending, active, running, error. Ссылка на незарегистрированный action/data — pending, не ошибка. Невалидная страница — состояние **Invalid** с текстом, не падение.
- Опрос data_id по их интервалам, пока страница открыта.
- Вызов action: ключ по `risk` (`critical` — свежий Face ID), `confirm: true` — локальный диалог, параметры из полей ввода, показ `message` и обновление связанных данных.
- Pages: список с бейджами Draft / Invalid / Pending; Draft → **Accept** (`normal`); «Ожидают регистрации» с **Register** (`critical`).
- Правка на телефоне: переименовать, переставить секции и компоненты, удалить компонент, закрепить в Quick Access; **+ Page** → Chat с подготовленным запросом.
- Quick Access на Home заполняется.

**Тесты** — все page-векторы valid/invalid с совпадением текста ошибки; таблица тестов выражений; каждый компонент и layout рендерится; UI: страница от fake rh-agent с кнопкой, toggle и списком.

**От сервера** — `contracts/pages/rh.page.v1.schema.json`, page-векторы, API страниц (список, версия, Accept, правки с телефона, Quick Access), реестры action/data, вызов action.

**[проверить]** — нет своих.

**Владелец** — приёмка: агент по запросу в чате создаёт рабочую страницу с кнопкой, toggle и списком.

### Этап 6. Terminal

**Задачи**
- SSH к стандартному sshd macOS через tailnet утверждённой библиотекой; подписант — ключ `ssh` из Secure Enclave (`ecdsa-sha2-nistp256`), Face ID на подключение.
- Эмулятор терминала, несколько сессий вкладками, панель клавиш esc, tab, ctrl, стрелки, `|`, `~`.
- Ядро в SSH не участвует, approval нет.

**Тесты** — кодирование публичного ключа и подписи в формате SSH по векторам, сгенерированным `ssh-keygen`; панель клавиш отдаёт правильные байты; подключение — ручная проверка (sshd на CI-раннере недоступен).

**От сервера** — добавление публичного ключа `ssh` в `~/.ssh/authorized_keys` по подтверждению владельца; адрес хоста для SSH.

**[проверить]** — §8.4 Swift-библиотека SSH с внешним подписантом и эмулятор терминала (кандидаты проверю по актуальной документации; выбор — **[утвердить]**). Исследование делаю заранее, в конце этапа 4, чтобы не ждать.

**Вопрос владельцу (И4)** — как проверять ключ хоста sshd: доверие при первом подключении (как обычный ssh, но это подтверждение сверх SPEC) или `rhcore pair` кладёт ключи хоста в подписанный ответ pair уже на этапе 1 (без лишних вопросов и без повторного pairing). Рекомендую второе, предложено серверу.

**Владелец** — включить Remote Login; работа в терминале Mac с телефона (обязательная физическая приёмка).

### Этап 7. Развёртывание

**Задачи**

- Полная пошаговая инструкция владельцу: установка Release-сборки на iPhone и pairing с рабочим ядром.

**От сервера** — рабочий адрес ядра (MagicDNS, порт) и сертификат.

**Владелец** — установка по инструкции без доработок (приёмка).
